Produto e escopo

O alvo é um marketplace comercializável para aluguel de estúdios audiovisuais em Curitiba/PR, em PT-BR, BRL e fuso America/Sao_Paulo.

Aplicações e pacotes

A separação entre público e administração já existe de verdade. Neste momento, ambos mostram apenas uma superfície técnica de fundação — não telas falsas de produto.

Implementado

Web público · raiz · porta 3000

Next.js App Router com página de status da fundação, layout responsivo, tokens compartilhados, CSP por request e endpoints /api/health/live e /api/health/ready.

Rotas de catálogo, autenticação, conta, dono, checkout e comandos ainda não existem.

Implementado

Backoffice · apps/backoffice · porta 3001

Aplicação Next.js independente, noindex, build e runtime próprios, CSP e health/readiness separados. O app público não expõe /admin.

Revisão, usuários, taxonomias, financeiro, fiscal, jobs e auditoria chegam nas FEAT-030 a FEAT-033; ainda não há acesso administrativo funcional.

Implementado

packages/contracts

Contratos Zod de health, release e URL DAL; readiness server-only; tipos gerados do banco. O schema público permanece vazio porque nenhuma entidade de negócio foi antecipada.

Implementado

packages/ui

Tokens claro/escuro e o componente técnico FoundationStatus, com reflow, safe areas e redução de movimento. Primitives de produto entram apenas quando houver consumidor real.

Gates canônicos:

npm ci → format → lint → typecheck → unit → Supabase reset → pgTAP/drift → docs → Playwright completo → builds → audit → Knip. No último ciclo concluído, todos ficaram verdes e o audit registrou zero vulnerabilidades.

Segurança e local-first

A etapa atual usa somente a máquina local e Supabase via Docker. A fundação nasce fechada e só ampliará acesso junto com cada feature real.

Banco e readiness

Sete migrations append-only criam os schemas internos, a role app_dal e probes de readiness. Não há tabela de negócio. Grants, owners, memberships e ACLs públicas são comparados com allowlists exatas.

Runtime web

CSP com nonce novo por request, headers seguros, fallback sem JavaScript, health sem cache e readiness que falha fechado sem expor SQL, credencial ou diagnóstico interno.

Ambiente e supply chain

Docker restrito ao loopback, arquivos env 0600, subprocessos por allowlist, logs redigidos, versões exatas, lockfile único, lifecycle scripts bloqueados, audit e Knip obrigatórios.

  • nenhum secret público
  • nenhum service role no browser
  • app público sem admin
  • URL DAL local validada
  • grants explícitos; RLS entra por tabela
  • erros públicos seguros
  • artefatos E2E só em falha
  • sem API externa

Release e deploy

Já existe um caminho local reproduzível para o artefato. Infraestrutura real e go-live permanecem deliberadamente bloqueados pelo ADR-018.

Reprodutibilidade e falha segura

Lock exclusivo, tar com ordem/tempo/ownership/modos normalizados, checksum, extração de verificação, recusa de sobrescrita divergente, varredura de secrets e limpeza de processos em interrupção.

Validado localmente no 14º review

Cleanup físico de artefatos

O patch atual usa /proc/self/mountinfo, inspeção por lstat, rename atômico e revalidação antes de remover árvores; falha fechado quando não pode provar a topologia.

Regra de verdade:

Uma feature só muda para concluída quando banco, contratos, UI desktop/mobile, acessibilidade, Playwright, documentação, observabilidade e rollback aplicáveis estão verdes. Interface isolada ou mock não conta como feature implementada.

Próximos passos e pendências

Primeiro termina a fundação; depois as features avançam uma por vez, em branches e PRs independentes, sem antecipar tela, schema ou integração de outra feature.

Próxima execução

  1. Resolver somente os comentários efetivamente atendidos no ciclo publicado. O comentário rejeitado permanece aberto com evidência.
  2. Solicitar novo @codex review e esperar 60 minutos antes de consultar. A espera de 4 horas foi uma exceção pontual do ciclo instruído.
  3. Repetir correção, testes e review até não haver problema acionável.
  4. Após o merge, abrir uma branch exclusiva para a FEAT-002 (autenticação).

Fluxo obrigatório por feature

  1. Ler contratos e criar o registro em docs/changes/.
  2. Entregar uma fatia vertical completa com correção e estados de UX.
  3. Atualizar este HTML, docs da feature, banco e QA no mesmo PR.
  4. Rodar todos os gates e a suíte Playwright completa.
  5. Fazer review, corrigir, publicar e resolver threads atendidas antes do merge.
