Arquitetura

  • Next.js 16 App Router, React 19, TypeScript estrito e CSS Modules.
  • Supabase Auth/Postgres/Storage; migrations append-only, grants mínimos e RLS.
  • Leituras por read models pequenos; escritas críticas por API, DAL e função SQL privada.
  • Web por HTTPS no IP reservado, com certificado curto, renovação automática e barreira de 24 horas de validade mínima; backoffice separado na 3001 e somente em loopback. A aplicação pública ainda depende do primeiro deploy.
  • Releases standalone Linux x86_64 mantêm código e ambientes do mesmo SHA; ativação atômica, readiness e recuperação automática preservam a versão anterior em caso de falha ou reboot. A recuperação de serviços aguarda rede online e Nginx antes de consumir o marcador de rollback e só o remove após health interno e público. O bootstrap só reutiliza diretórios existentes após validar o marcador operacional ou um marcador transitório root-only, abre as raízes de release sem seguir symlink e mantém boot e deploy bloqueados durante a mutação. Antes de liberar uma release compatível, arma o mesmo recovery de rollback e só o desarma após readiness; falha republica o bloqueio antes de retirar o symlink. O instalador root readquire o lock fechado pelo sudo antes de copiar os inputs, de modo que uploads concorrentes não alteram a release em validação. Um ponteiro pendente é removido antes da próxima validação para permitir reparo por release aprovada. Archives são pré-varridos em streaming com limites próprios para headers PAX/GNU antes da extração. A reutilização de um SHA compara deterministicamente toda a árvore instalada com a candidata e recusa qualquer adulteração, mesmo quando o marcador do artifact não mudou.
  • O login DAL só é habilitado após provar que não alcança pg_net e que nenhum catálogo gerenciado legível contém configuração nomeada como segredo. A membership reversa de app_runtime_production aceita somente a administração automática de postgres, sem permissão para assumir a role. Readiness também bloqueia grants do schema ou de comandos privados para qualquer grantee além do owner/DAL e exige que o schema private e todas as suas rotinas pertençam ao owner canônico postgres. Os comandos allowlisted permanecem security definer com search_path = ''; membership, ownership ou acesso efetivo de app_dal a schema externo fora das allowlists também são recusados. A release anterior só é preservada quando seu schema permanece aplicado e compatível. Chaves Supabase privilegiadas ou JWT são recusadas antes dos builds; produção aceita somente o formato sb_publishable_.

Qualidade e entrega

Cada feature usa branch própria. Antes do merge passam format, lint, tipos, Vitest, banco, documentação, Playwright, build, audit e Knip conforme o risco. Todo PR recebe @codex review, espera real mínima de 60 minutos e novos ciclos depois de cada correção até uma declaração explícita de review limpo no SHA atual.

O CI repete os gates em Windows e Linux limpos, incluindo unitários, SQL/RLS, Playwright multiengine, acessibilidade, builds standalone e contratos de host. Callbacks usados apenas por traps têm compatibilidade estática anotada de forma pontual, sem desativar regra global. Testes não usam retry, timeout ampliado ou relaxamento de asserção para mascarar falhas; uma falha Playwright retém seus artifacts diagnósticos por sete dias, enquanto resultados de cada execução permanecem no PR e nos checks.

O bootstrap local fixa o named pipe/socket Docker canônico antes de qualquer operação Supabase. O banco mantém os catálogos sensíveis negados às roles da aplicação e preserva para supabase_storage_admin somente a leitura de pg_roles exigida pelas migrations oficiais do Storage.

Merge em main aplica migrations forward-only e publica uma release imutável na VM, com health interno e público, rollback e recuperação após interrupção. Timeout ou serviço indisponível é inconclusivo; falha pós-merge abre nova branch e repete o ciclo. Antes de aceitar a chave de entrega, o bootstrap valida a identidade canônica, os grupos, o home, o shell e o bloqueio de senha de cada conta operacional.

Princípios operacionais

  • Sem gambiarra em produção; experimento local explícito e reversível é permitido.
  • Uma fonte canônica por fato e documentação sem copiar histórico de execução.
  • Complexidade precisa de requisito, ameaça ou métrica concreta.
  • Playwright prova comportamento visível; unitários e SQL protegem lógica e invariantes.
  • Plano de feature é removido depois do merge/deploy concluído.
