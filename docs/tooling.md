# Tooling e comandos do repositório

## 1. Runtime reproduzível

- Node.js `24.18.0`, fixado em `.nvmrc`, `.node-version`, `engines` e `devEngines`;
- npm `11.19.0`, fixado em `packageManager` e `devEngines`;
- um único `package-lock.json` para todos os workspaces;
- `npm ci` é o bootstrap reproduzível; `npm install` somente altera dependências deliberadamente;
- dependências e ferramentas adotadas ficam em `docs/dependencias-utilizadas.md`.

## 2. Workspaces

```json
{
  "workspaces": ["apps/*", "packages/*"]
}
```

A aplicação pública é o package raiz. `apps/backoffice` é a aplicação administrativa separada. `packages/contracts` e `packages/ui` são compartilhados e não criam um terceiro sistema visual ou domínio paralelo.

`npm run dev`, `npm run dev:backoffice` e `npm run dev --workspace @set-livre/backoffice` convergem no mesmo launcher single-app; nenhum desses scripts chama `next` ou outro `npm run` diretamente. O launcher relê o `.env.local` físico `0600` da aplicação, exige os seis nomes runtime exatos, comprova aplicação, Supabase e identidade DAL local restrita no host escrito literalmente como `127.0.0.1` e constrói o ambiente filho por allowlist. Um único parser lexical é compartilhado por launchers, bootstrap, psql, E2E e release; ele recusa `localhost`, IPv6 e representações alternativas de IPv4 antes que a normalização de URL possa torná-las equivalentes. Antes de resolver ou iniciar a CLI, também recusa `.env`, `.env.development` e `.env.development.local` no diretório de cada app, impedindo que o carregador interno do `next dev` acrescente uma segunda fonte em disco. Assim, uma `DATABASE_URL_APP_DAL` cloud, credencial E2E, opção Node/npm, loader ou secret exportado no host não substitui o arquivo local nem chega ao processo Next. Node vem de `process.execPath`; a CLI Next é um caminho absoluto, sem shell ou lookup em `PATH`, e precisa ser arquivo físico protegido cujo manifesto, versão exata e declaração `bin` correspondam ao `next` fixado no manifesto raiz.

Os filhos `next dev` são serviços persistentes: uma saída natural nunca representa conclusão bem-sucedida, inclusive quando o filho informa código `0`. Nesse caso o launcher registra a saída real para diagnóstico, devolve código `1` e encerra as demais árvores antes de concluir. O supervisor só conclui com `0` depois de um shutdown explicitamente solicitado; a fase finita de build do preview converte sua conclusão esperada nesse shutdown antes do handler genérico de serviços. Encerramentos solicitados por sinal preservam seus códigos próprios.

`npm start`, `npm run start:backoffice` e `npm run start --workspace @set-livre/backoffice` também convergem em `scripts/local-production-server.mjs`, sem `next` ou npm filho nos manifests. Esse preview relê o `.env.local` físico uma vez, reaplica o contrato local exato e rejeita `.env`, `.env.production` e `.env.production.local`. Com handlers de sinal instalados antes da primeira factory, no Linux recusa uma `.next` não física, em dispositivo diferente do pai ou que seja/contenha mount enumerado por `/proc/self/mountinfo`; a árvore inteira é inspecionada por `lstat` sem atravessar symlinks, e suas identidades físicas precisam permanecer iguais antes e depois do `rename` atômico para um irmão exclusivo. Só então a árvore retirada é removida e `next build` pode iniciar. Em macOS, Windows e outros sistemas, onde a API Node não enumera todos os tipos de mount de forma universal, qualquer `.next` existente falha antes de reservar o retiro, renomear, remover ou spawnar; o operador deve inspecionar e remover a árvore manualmente, enquanto sua ausência permite o build fresco. Somente após código `0` e um `BUILD_ID` novo válido o launcher executa `next start` em `127.0.0.1`. Ambas as fases usam o mesmo ambiente por allowlist, Node atual e CLI Next absoluta, sem shell. Saída natural do servidor, inclusive código `0`, é falha; `SIGHUP`, `SIGINT` e `SIGTERM` limpam o PGID completo e preservam `129`, `130` e `143`. No Windows, a árvore permanece identificada mesmo depois da saída natural do root e recebe uma tentativa síncrona de `taskkill /T /F` antes da conclusão. Variáveis cloud, E2E, Node/npm, PG, SSH e secrets herdados não chegam a build ou servidor, e um bundle `.next` anterior nunca é reutilizado. A remoção segura pressupõe que nenhum outro writer altere `.env.local`, `.next`, toolchain ou checkout durante a inspeção, o retiro e o fluxo. A release continua iniciando os entrypoints standalone empacotados, sem depender desse launcher.

`node scripts/dev-all.mjs` faz o mesmo preflight para os dois apps antes do primeiro spawn e inicia diretamente as duas CLIs Next, sem uma camada npm intermediária. Em POSIX, cada filho lidera seu próprio PGID e recebe encerramento gracioso seguido de `SIGKILL`; no Windows, a árvore inteira é encerrada pelo `taskkill.exe` absoluto e limitado. Se qualquer filho terminar sozinho, inclusive com código `0`, o supervisor transforma esse zero inesperado em falha, limpa a outra árvore em ambas as plataformas e propaga explicitamente o resultado pelo processo `dev-all`. Os comandos npm diretos agora não contornam o guard, mas o npm pai, seu shell e eventuais `NODE_OPTIONS` já executaram antes de o código do launcher assumir controle; a fronteira não promete recuperar um chamador ou preloader já comprometido. Para eliminar essa etapa anterior, execute `node scripts/local-development-server.mjs web|backoffice` ou `node scripts/dev-all.mjs` a partir de Node `24.18.0` e shell confiáveis. Em todos os casos, a garantia também pressupõe que nenhum principal com permissão de escrita altere Node, npm, Next, checkout ou qualquer arquivo `.env*` durante toda a vida do servidor; não existe vínculo atômico portátil entre inspeção e execução. O validador da URL DAL é compartilhado com o smoke de release.

Os artefatos rastreados do banco nunca são o destino direto de uma CLI. `supabase:schema` entrega ao dump um arquivo temporário exclusivo e irmão de `schema.generated.sql`; depois de saída bem-sucedida, reabre o arquivo e comprova sua identidade física estável antes de qualquer escrita, recusa saída vazia ou sem declarações de `audit`, `private` e `public`, normaliza a quebra de linha final, restaura o modo do destino, sincroniza o descritor e publica com `rename` atômico. `supabase:types` aplica o mesmo contrato de publicação a `database.generated.ts`, além de exigir os exports esperados, validar a sintaxe TypeScript e aplicar a configuração Prettier do repositório. Falha de Docker, stack, CLI, leitura, normalização, validação ou formatação remove por nome somente o respectivo temporário e preserva integralmente a versão anterior.

O gate obrigatório `test:db` roda essa geração novamente depois do pgTAP, mas aponta os helpers atômicos para dois destinos irmãos exclusivos que mantêm as extensões `.sql` e `.ts`. A raiz confiável e cada ancestral precisam ser diretórios físicos; arquivos rastreados e candidatos usam leitura com `O_NOFOLLOW`, e sua identidade e seus bytes são revalidados depois dos dois geradores antes da comparação. O gate não chama outro `npm`, não reinvoca o próprio comando e não publica saída: divergência em `supabase/schema.generated.sql` ou `packages/contracts/src/database.generated.ts` falha com orientação para executar `npm run supabase:generate` e versionar os contratos. O cleanup tenta os dois nomes exatos mesmo se o primeiro falhar, agrega esse diagnóstico sem mascarar a causa principal e nunca remove diretórios recursivamente.

Para drift de ACL em catálogos pertencentes a `supabase_admin`, o pgTAP abre uma conexão administrativa local isolada via `dblink`, altera somente uma transação e sempre executa `ROLLBACK` antes de provar a recuperação. A cobertura de rotinas distingue overloads por OID, adultera especificamente `pg_read_file(text)` e cria uma função normal efêmera em `pg_catalog`; nenhuma dessas mudanças sobrevive ao teste.

`node scripts/release-manifest.mjs` exige checkout limpo e uma `.artifacts` física dentro do repositório antes de qualquer remoção. No Linux, antes de alterar permissões, adquirir o lock ou iniciar o build, o script lê `/proc/self/mountinfo` do namespace atual e recusa a própria `.artifacts` quando ela é um mount; leitura ausente, vazia ou malformada falha fechada. A entrada direta evita configuração do npm pai; antes do primeiro build, o script deriva e valida a instalação Node/npm adjacente e lê a versão do manifesto npm fixado, sem executar `npm.cmd`, shell ou lookup em `PATH`, sob a mesma fronteira confiável descrita para desenvolvimento. No ambiente Linux de release, um lock advisory exclusivo do `util-linux flock` é adquirido por descritor antes de ler o SHA e permanece ativo durante builds, montagem de `releaseRoot`, smoke, temporários, verificação e publicação. Uma segunda invocação espera o mesmo lock; o kernel o libera se o processo encerra, e o arquivo físico `release.lock` não deve ser removido porque seu inode estável é parte da exclusão mútua. Ausência da instalação validada falha antes do build com erro explícito, e o subprocesso herda somente a allowlist operacional.

Cada app é recompilado com seu próprio `.env.local` obrigatório, limitado aos seis nomes runtime documentados, `BUILD_ID` igual ao SHA e uma allowlist operacional; outros arquivos `.env` de produção, credenciais E2E, banco, tokens, opções de processo e secrets não são herdados pelo build. Antes de ler qualquer valor, a release exige arquivo físico regular exclusivo em modo `0600`, abre com `O_NOFOLLOW` e comprova por descritor a mesma identidade de dispositivo/inode, quantidade de links e modo antes e depois da leitura. Só então o conteúdo é interpretado e validado como runtime local exato da aplicação. O pacote inclui static/public/migrations e o lockfile, recusa configuração local, secret conhecido e link externo, e revalida hashes e o conjunto exato de nós da release após o smoke.

Depois o comando instala `SIGHUP`/`SIGINT`/`SIGTERM` antes do primeiro spawn e inicia exatamente `web/server.js` e `backoffice/apps/backoffice/server.js` com ambientes runtime separados. A URL DAL vem exclusivamente do `.env.local` do respectivo app e precisa comprovar protocolo PostgreSQL, host IPv4 literal `127.0.0.1`, porta `54322`, login `app_runtime_local`, banco `postgres` e `options=-c role=app_dal`; uma `DATABASE_URL_APP_DAL` exportada no host nunca a substitui. Em POSIX, cada servidor lidera um PGID detached; qualquer interrupção percorre o mesmo cleanup dos dois grupos, mantém o PGID rastreado mesmo se o líder sair, aplica `SIGKILL` após a janela graciosa e preserva os códigos `129`, `130` ou `143`. O smoke exercita páginas, health, readiness, headers e asset estático, redige eventual log de falha e produz tar/checksum determinísticos a partir do timestamp do commit. Além de ordem, tempo e ownership, o GNU tar normaliza diretórios e executáveis para `0755` e arquivos regulares não executáveis para `0644`, tornando o pacote independente do `umask`. O tar candidato é reextraído em diretório privado e comparado, por tipo e hash, à árvore validada antes de ser publicado. Um artefato já existente para o mesmo SHA só é reutilizado se os bytes forem idênticos; conteúdo divergente nunca é sobrescrito. O manifesto registra plataforma/arquitetura; validação ARM64 continua bloqueada por PEND-003.

Qualquer árvore gerada antiga (`release` ou diretório de verificação `.incoming`) só entra em remoção recursiva depois de comprovar ancestrais físicos, tipo de cada nó por `lstat` sem atravessar links, dispositivo compatível e ausência de mount na raiz ou em descendentes segundo o mesmo `mountinfo`. A árvore é retirada por `rename` atômico para um irmão exclusivo, e identidade, forma e mounts são revalidados no novo caminho antes de `rm`. Um arquivo gerado exato é removido apenas como arquivo físico; link ou nó especial é recusado. Em plataformas sem a prova Linux, uma árvore existente falha antes de rename ou remoção e requer inspeção manual; alvo ausente continua sendo no-op. Esse contrato impede que o cleanup atravesse volumes ou bind mounts esquecidos, inclusive no mesmo dispositivo, mas continua pressupondo ausência de um principal privilegiado que altere mounts ou a árvore concorrentemente.

Os launchers diretos `scripts/dev-all.mjs`/`scripts/release-manifest.mjs` e os workers em `tests/fixtures/` são entradas explícitas do Knip porque não dependem de import estático. O binário de sistema `flock`, versionado e documentado na matriz de dependências, é a única exceção de binário externo da análise.

- ESLint 9 e configs Next/TypeScript alinhados à versão do framework;
- regras React, hooks, Core Web Vitals, imports, ciclos, promises, `any` e `console`;

## 6. Formatting

O Blueprint tem checksum canônico e não é reformatado. `scripts/format-scope.mjs` verifica todo código/config mantido e o Markdown alterado, inclusive depois do commit da branch. Entre `origin/main` e `main` local, a base Git escolhida é a candidata válida cujo `merge-base` está a menos commits de `HEAD`; assim uma ref remota atrasada não amplia o diff com trabalho já incorporado à `main` local. Em uma feature recém-criada no mesmo commit da candidata, o próprio `HEAD` é a base e somente mudanças working/staged/untracked podem exigir o novo registro; no checkout da própria `main`, a candidata idêntica continua cedendo ao histórico alcançável para preservar a verificação de seus commits. Empates preservam a precedência remota e, sem candidata útil, o gate usa o commit raiz alcançável; em um repositório ainda no commit inicial, todos os arquivos rastreados entram no conjunto. Os filtros incluem mudança de tipo Git `T`, portanto trocas entre arquivo regular e symlink permanecem no escopo documental e de formatação; antes de ler ou escrever qualquer candidato, o formatador rejeita symlinks e nós especiais com erro controlado, sem seguir um alvo externo. A ausência ou defasagem da ref remota nunca elimina Markdown commitado nem permite reutilizar um change record anterior. Prettier não substitui lint ou validação documental.

## 7. Playwright e axe

Pré-requisito de máquina:

```bash
npm run test:e2e:install
```

O config parseia `.env.e2e.local` sem contaminar `process.env`, rejeita origem/host/protocolo/porta remotos, exige `E2E_ALLOW_LOCAL=1` e comprova por conexão um marcador efêmero da instância. Depois que o runner Playwright é iniciado por uma toolchain confiável, um overlay neutraliza todos os nomes herdados antes do merge interno de cada webServer e restaura somente a allowlist operacional. O comando usa o executável Node absoluto e um wrapper single-app versionado; esse wrapper reutiliza o mesmo guard dos comandos dev, relê o `.env.local` físico, valida a CLI Next fixada, preserva os valores runtime/anon locais, substitui somente `APP_ENV=test` e inicia Next diretamente, sem npm filho ou shell. No POSIX, o prefixo `exec` mantém wrapper e Next no PGID que o Playwright controla; `SIGHUP`/`SIGINT`/`SIGTERM` são encaminhados e o fechamento solicitado conclui com limpeza `SIGKILL` do grupo. No Windows, o runner encerra a árvore pelo `taskkill.exe` absoluto derivado de `SystemRoot/System32`, com `/PID`, `/T` e `/F`, sem shell nem lookup em `PATH`; o utilitário recebe somente `SystemRoot` e `WINDIR`, nunca a DAL ou os secrets do app, e cada tentativa fica limitada a cinco segundos. Credencial administrativa, npmrc remoto, secrets e valores PG/SSH herdados não alcançam os apps após essa fronteira; cada app recebe somente sua DAL restrita e o runtime local validado. A matriz cobre 1440×900, 390×844, 320×720, altura compacta, backoffice isolado, axe claro/escuro/mobile e os fluxos críticos nos três engines, com retries zero e artefatos somente em falha.

O processo de cada browser recebe uma allowlist operacional independente do ambiente dos apps: paths/home/temporários, locale/fuso/terminal, variáveis gráficas locais não ligadas a Snap e os equivalentes mínimos do Windows. Segredos, URLs de banco, SSH, npm, opções Node, variáveis `SNAP*`, `LD_*`/`DYLD_*` e qualquer nome não enumerado nunca são herdados. Segmentos Snap e entradas vazias também são removidos do `PATH`/`Path`, evitando tanto bibliotecas do host incompatíveis quanto resolução pelo diretório atual.

## 8. Supabase local

`npm run supabase:reset` executa:

1. comprovação do daemon Docker;
2. criação idempotente da bridge `set-livre-loopback`, cujo default de publicação é `127.0.0.1` sem alterar o daemon Docker;
3. parada restrita à stack `set-livre` se containers preexistentes estiverem em outra rede ou binding;
4. `supabase start --network-id set-livre-loopback`, validação dos bindings efetivos e `supabase db reset --local`;
5. migrations e seed;
6. autenticação local explícita como `supabase_admin` superuser, usando a mesma credencial efêmera da stack e sem expô-la, para fechar `public`/`net`, defaults gerenciados, catálogos sensíveis e membros residuais de `app_dal`/login;
7. criação/rotação local de `app_runtime_local` com estado exato e somente `CONNECT` direto;
8. reconciliação exata das duas referências a `app_dal`: `postgres` administrativa sem `SET/INHERIT` e runtime sem `ADMIN/INHERIT` com `SET` explícito;
9. smoke da identidade efetiva e das duas probes privadas de readiness antes de publicar qualquer ambiente;
10. gravação separada dos dois `.env.local` de runtime e de `.env.e2e.local`, todos com modo `0600`, sem imprimir secrets.

A normalização e a probe usam o mesmo caminho absoluto de `psql`, host numérico `127.0.0.1`, porta `54322`, senha local controlada, `--no-password` e `--no-psqlrc`. Antes de o fluxo iniciar Supabase ou obter qualquer credencial, o preflight POSIX aceita em `PATH` somente segmentos absolutos canônicos, inspeciona a cadeia de links e ancestrais físicos protegidos por `root`, registra owner/mode/dev/ino/nlink e exige que o próprio candidato informe exatamente PostgreSQL `18.4` sob ambiente sem senha e sem `PATH`. O snapshot é revalidado antes de interpretar cada URL, imediatamente antes e depois dos três spawns; o caminho executado continua sendo o candidato original validado, não seu `realpath`, para preservar o contrato de wrappers como `pg_wrapper`. Cada processo recebe somente `LANG=C`, `LC_ALL=C` e `PGPASSWORD` controlada; a probe DAL acrescenta o `PGOPTIONS` exato que assume `app_dal`. Nenhum outro `PG*`/`PSQL*`, `PATH`, home, locale, service/passfile, TLS/GSS, loader ou secret herdado sobrevive, portanto até `PGHOSTADDR` não altera o destino local. No Windows nativo o setup falha fechado após a validação inicial do contexto Docker e antes do start/reset ou acesso a credenciais, pois esta implementação não dispõe de uma prova equivalente sem reparse point; WSL usa o caminho POSIX. npm/shell/Node e as CLIs Docker/Supabase continuam sendo a toolchain global confiável e não são cobertos pelo guard específico de `psql`. Também não há vínculo atômico portátil entre revalidação e execução: alteração concorrente por um escritor privilegiado permanece fora da fronteira.

A URL administrativa fica em `E2E_DATABASE_URL` somente no arquivo do harness. Runtime usa `DATABASE_URL_APP_DAL` com `SET ROLE app_dal`. Antes de qualquer branch, inclusive `stop`, bootstrap e wrappers recusam overrides Docker remotos, exigem o contexto `default`, comprovam o socket/named pipe local e pinam esse endpoint no ambiente de cada comando Docker/Supabase. Os wrappers de start/status/test/dump/types recusam stack fora da bridge; todo `stderr` fica em pipe privado e é descartado, falhas substituem integralmente buffers e erro original, e o status completo com chaves nunca é impresso. Somente o `stdout` necessário a pgTAP e geração de tipos pode ser herdado. Nenhuma migration contém senha e nenhum comando usa `supabase link` ou cloud.

## 9. Knip e supply chain

Knip descobre os quatro workspaces pelos manifests/configs. A única exceção de dependência é restrita aos packages `@types/react` e `@types/react-dom` necessários ao JSX do pacote UI. Entre binários de sistema registrados, `flock` pertence somente ao runtime do gerador de release Linux e `mkfifo` somente à fixture unitária adversarial em POSIX; ambos ficam explícitos em `ignoreBinaries`, sem ocultar package npm, import ou código morto. `npm audit --audit-level=high`, `ignore-scripts=true`, `strict-allow-scripts=true` e `dangerously-allow-all-scripts=false` completam o gate: `npm ci` não executa lifecycle de dependência, root ou workspace, nenhuma entrada `allowScripts` é aceita e um override isolado de `ignore-scripts` ainda falha no preflight estrito. Esse contrato pressupõe a invocação canônica sem override `NPM_CONFIG_*` hostil; um chamador já comprometido está fora da fronteira.

`docs:check` também calcula o conjunto externo direto dos quatro manifests canônicos, incluindo dependências de runtime, desenvolvimento, opcionais e peers. Cada pacote precisa aparecer uma única vez em `docs/dependencias-utilizadas.md`, com nome e versão semver exatos, superfície, licença, justificativa e avaliação de supply chain; registros ausentes, extras, agrupados, duplicados ou incompletos falham. Specs com alias npm, faixa ou formato ambíguo também falham. Enquanto o registro não representar replacements sem ambiguidade, qualquer `overrides` não vazio é recusado, inclusive troca de versão ou alias para outro pacote. Dependências `@set-livre/*` não entram como terceiros: o gate exige que apontem exatamente para nome e versão de um dos workspaces físicos canônicos.

## 10. Docs check

O gate falha, entre outros casos, quando:

- o Blueprint muda sem novo contrato;
- feature, cenário ou ADR duplica ID;
- a sequência não contém exatamente as 34 features;
- `dependency-to-start` cria ciclo ou aponta para frente;
- integração posterior não possui proprietário;
- dependência de release não referencia `pendencias.md`;
- link local está quebrado;
