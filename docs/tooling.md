# Tooling e comandos do repositório

## 1. Runtime reproduzível

- Node.js `24.18.0`, fixado em `.nvmrc`, `.node-version`, `engines` e `devEngines`;
- npm `11.19.0`, fixado em `packageManager` e `devEngines`;
- workstation de desenvolvimento em Windows 11 nativo, sem WSL, com Node/npm instalados fisicamente lado a lado e PowerShell oficial `7.6.5` instalado pelo MSI x64; o MSIX redundante foi removido depois da validação do binário físico, hash oficial e assinatura Microsoft;
- caminhos longos do Windows estão habilitados e o checkout preserva LF e semântica NTFS com `core.autocrlf=false`, `core.filemode=false`, `core.symlinks=false`, `core.longpaths=true`, `core.ignorecase=true` e `core.protectNTFS=true`;
- um único `package-lock.json` para todos os workspaces;
- `npm ci` é o bootstrap reproduzível em uma árvore nova da plataforma atual; `node_modules` copiado de Linux não é reutilizável no Windows;
- `npm install` somente altera dependências deliberadamente;
- dependências e ferramentas adotadas ficam em `docs/dependencias-utilizadas.md`.

O ADR-022 estabelece a política de correção canônica. Nenhum gate pode ser obtido por workaround,
supressão de erro, bypass, downgrade oportunista, edição manual de gerado ou relaxamento de teste. Uma
incompatibilidade exige remoção completa da abordagem inadequada e adoção da solução suportada com
testes e documentação; sem essa prova, a operação permanece fail-closed e explicitamente pendente.

## 2. Workspaces

```json
{
  "workspaces": ["apps/*", "packages/*"]
}
```

A aplicação pública é o package raiz. `apps/backoffice` é a aplicação administrativa separada. `packages/contracts` e `packages/ui` são compartilhados e não criam um terceiro sistema visual ou domínio paralelo.

`npm run dev`, `npm run dev:backoffice` e `npm run dev --workspace @set-livre/backoffice` convergem no mesmo launcher single-app; nenhum desses scripts chama `next` ou outro `npm run` diretamente. O launcher relê o `.env.local` físico protegido da aplicação, exige os seis nomes runtime exatos, comprova aplicação, Supabase e identidade DAL local restrita no host escrito literalmente como `127.0.0.1` e constrói o ambiente filho por allowlist. Um único parser lexical é compartilhado por launchers, bootstrap PostgreSQL, E2E e release; ele recusa `localhost`, IPv6 e representações alternativas de IPv4 antes que a normalização de URL possa torná-las equivalentes. Antes de resolver ou iniciar a CLI, também recusa `.env`, `.env.development` e `.env.development.local` no diretório de cada app, impedindo que o carregador interno do `next dev` acrescente uma segunda fonte em disco. Assim, uma `DATABASE_URL_APP_DAL` cloud, credencial E2E, opção Node/npm, loader ou secret exportado no host não substitui o arquivo local nem chega ao processo Next. Node vem de `process.execPath`; a CLI Next é um caminho absoluto, sem shell ou lookup em `PATH`, e precisa ser arquivo físico protegido cujo manifesto, versão exata e declaração `bin` correspondam ao `next` fixado no manifesto raiz.

Os filhos `next dev` são serviços persistentes: uma saída natural nunca representa conclusão bem-sucedida, inclusive quando o filho informa código `0`. Nesse caso o launcher registra a saída real para diagnóstico, devolve código `1` e encerra as demais árvores antes de concluir. O supervisor só conclui com `0` depois de um shutdown explicitamente solicitado; a fase finita de build do preview converte sua conclusão esperada nesse shutdown antes do handler genérico de serviços. Encerramentos solicitados por sinal preservam seus códigos próprios.

`npm start`, `npm run start:backoffice` e `npm run start --workspace @set-livre/backoffice` também convergem em `scripts/local-production-server.mjs`, sem `next` ou npm filho nos manifests. Esse preview relê o `.env.local` físico uma vez, reaplica o contrato local exato e rejeita `.env`, `.env.production` e `.env.production.local`. Com handlers de sinal instalados antes da primeira factory, no Linux recusa uma `.next` não física, em dispositivo diferente do pai ou que seja/contenha mount enumerado por `/proc/self/mountinfo`; a árvore inteira é inspecionada por `lstat` sem atravessar symlinks, e suas identidades físicas precisam permanecer iguais antes e depois do `rename` atômico para um irmão exclusivo. No Windows, a remoção valida alvo autorizado, volume e identidade físicos, recusa reparse points, retira a árvore para um irmão exclusivo e revalida a árvore retirada antes da exclusão. Só então `next build` pode iniciar. Em macOS e outras plataformas sem prova implementada, uma `.next` existente falha antes de rename, remoção ou spawn e requer inspeção manual. Somente após código `0` e um `BUILD_ID` novo válido o launcher executa `next start` em `127.0.0.1`. Ambas as fases usam o mesmo ambiente por allowlist, Node atual e CLI Next absoluta, sem shell. Saída natural do servidor, inclusive código `0`, é falha; `SIGHUP`, `SIGINT` e `SIGTERM` limpam o PGID completo e preservam `129`, `130` e `143`. No Windows, build e servidor são guardians distintos; cada alvo entra em Job Object antes de executar, e fechar o guardian elimina toda a árvore mesmo se a raiz já encerrou. Variáveis cloud, E2E, Node/npm, PG, SSH e secrets herdados não chegam a build ou servidor, e um bundle `.next` anterior nunca é reutilizado. A remoção segura pressupõe que nenhum outro writer altere `.env.local`, `.next`, toolchain ou checkout durante a inspeção, o retiro e o fluxo. A release continua iniciando os entrypoints standalone empacotados, sem depender desse launcher.

`node scripts/dev-all.mjs` faz o mesmo preflight para os dois apps antes do primeiro spawn e inicia diretamente as duas CLIs Next, sem uma camada npm intermediária. Em POSIX, cada filho lidera seu próprio PGID e recebe encerramento gracioso seguido de `SIGKILL`. No Windows, o guardian do ADR-023 cria cada alvo suspenso, associa-o a um Job Object antes do primeiro byte de aplicação e fecha toda a árvore por identidade de kernel em shutdown, falha do outro app, saída natural da raiz ou queda abrupta do supervisor. Qualquer filho persistente que termine sozinho, inclusive com código `0`, continua sendo falha; o outro Job é encerrado antes de `dev-all` concluir. O guardian é compilado pelo `csc.exe` físico do sistema a partir da fonte versionada, em cache privado versionado pelos bytes do compilador e dos dois fontes, sem pacote nativo ou fallback para `taskkill`. Os comandos npm diretos agora não contornam o guard, mas o npm pai, seu shell e eventuais `NODE_OPTIONS` já executaram antes de o código do launcher assumir controle; a fronteira não promete recuperar um chamador ou preloader já comprometido. Para eliminar essa etapa anterior, execute `node scripts/local-development-server.mjs web|backoffice` ou `node scripts/dev-all.mjs` a partir de Node `24.18.0` e shell confiáveis. Em todos os casos, a garantia também pressupõe que nenhum principal com permissão de escrita altere Node, npm, Next, checkout ou qualquer arquivo `.env*` durante toda a vida do servidor; não existe vínculo atômico portátil entre inspeção e execução. O validador da URL DAL é compartilhado com o smoke de release.

Os artefatos rastreados do banco nunca são o destino direto de uma CLI. `supabase:schema` entrega ao dump um arquivo temporário exclusivo e irmão de `schema.generated.sql`; depois de saída bem-sucedida, reabre o arquivo e comprova sua identidade física estável antes de qualquer escrita, recusa saída vazia ou sem declarações de `audit`, `private` e `public`, normaliza a quebra de linha final, restaura o modo do destino, sincroniza o descritor e publica com `rename` atômico. `supabase:types` aplica o mesmo contrato de publicação a `database.generated.ts`, além de exigir os exports esperados, validar a sintaxe TypeScript e aplicar a configuração Prettier do repositório. Falha de Docker, stack, CLI, leitura, normalização, validação ou formatação remove por nome somente o respectivo temporário e preserva integralmente a versão anterior.

O gate obrigatório `test:db` roda essa geração novamente depois do pgTAP, mas aponta os helpers atômicos para dois destinos irmãos exclusivos que mantêm as extensões `.sql` e `.ts`. A raiz confiável e cada ancestral precisam ser diretórios físicos; arquivos rastreados e candidatos usam leitura com `O_NOFOLLOW`, e sua identidade e seus bytes são revalidados depois dos dois geradores antes da comparação. O gate não chama outro `npm`, não reinvoca o próprio comando e não publica saída: divergência em `supabase/schema.generated.sql` ou `packages/contracts/src/database.generated.ts` falha com orientação para executar `npm run supabase:generate` e versionar os contratos. O cleanup tenta os dois nomes exatos mesmo se o primeiro falhar, agrega esse diagnóstico sem mascarar a causa principal e nunca remove diretórios recursivamente.

Para drift de ACL em catálogos pertencentes a `supabase_admin`, o pgTAP abre uma conexão administrativa local isolada via `dblink`, altera somente uma transação e sempre executa `ROLLBACK` antes de provar a recuperação. A cobertura de rotinas distingue overloads por OID, adultera especificamente `pg_read_file(text)` e cria uma função normal efêmera em `pg_catalog`; nenhuma dessas mudanças sobrevive ao teste.

`node scripts/release-manifest.mjs` é deliberadamente Linux-only e deve rodar no Ubuntu do CI/release, não na workstation Windows. Ele exige checkout limpo e uma `.artifacts` física dentro do repositório antes de qualquer remoção. Antes de alterar permissões, adquirir o lock ou iniciar o build, lê `/proc/self/mountinfo` do namespace atual e recusa a própria `.artifacts` quando ela é um mount; leitura ausente, vazia ou malformada falha fechada. A entrada direta evita configuração do npm pai; antes do primeiro build, deriva e valida a instalação Node/npm adjacente e lê a versão do manifesto npm fixado, sem executar `npm.cmd`, shell ou lookup em `PATH`, sob a mesma fronteira confiável descrita para desenvolvimento. Um lock advisory exclusivo do `util-linux flock` é adquirido por descritor antes de ler o SHA e permanece ativo durante builds, montagem de `releaseRoot`, smoke, temporários, verificação e publicação. Uma segunda invocação espera o mesmo lock; o kernel o libera se o processo encerra, e o arquivo físico `release.lock` não deve ser removido porque seu inode estável é parte da exclusão mútua. Ausência da instalação validada falha antes do build com erro explícito, e o subprocesso herda somente a allowlist operacional.

Cada app é recompilado com seu próprio `.env.local` obrigatório, limitado aos seis nomes runtime documentados, `BUILD_ID` igual ao SHA e uma allowlist operacional; outros arquivos `.env` de produção, credenciais E2E, banco, tokens, opções de processo e secrets não são herdados pelo build. Antes de ler qualquer valor, a release exige arquivo físico regular exclusivo em modo `0600`, abre com `O_NOFOLLOW` e comprova por descritor a mesma identidade de dispositivo/inode, quantidade de links e modo antes e depois da leitura. Só então o conteúdo é interpretado e validado como runtime local exato da aplicação. O pacote inclui static/public/migrations e o lockfile, recusa configuração local, secret conhecido e link externo, e revalida hashes e o conjunto exato de nós da release após o smoke.

Depois o comando instala `SIGHUP`/`SIGINT`/`SIGTERM` antes do primeiro spawn e inicia exatamente `web/server.js` e `backoffice/apps/backoffice/server.js` com ambientes runtime separados. A URL DAL vem exclusivamente do `.env.local` do respectivo app e precisa comprovar protocolo PostgreSQL, host IPv4 literal `127.0.0.1`, porta `54322`, login `app_runtime_local`, banco `postgres` e `options=-c role=app_dal`; uma `DATABASE_URL_APP_DAL` exportada no host nunca a substitui. Em POSIX, cada servidor lidera um PGID detached; qualquer interrupção percorre o mesmo cleanup dos dois grupos, mantém o PGID rastreado mesmo se o líder sair, aplica `SIGKILL` após a janela graciosa e preserva os códigos `129`, `130` ou `143`. O smoke exercita páginas, health, readiness, headers e asset estático, redige eventual log de falha e produz tar/checksum determinísticos a partir do timestamp do commit. Além de ordem, tempo e ownership, o GNU tar normaliza diretórios e executáveis para `0755` e arquivos regulares não executáveis para `0644`, tornando o pacote independente do `umask`. O tar candidato é reextraído em diretório privado e comparado, por tipo e hash, à árvore validada antes de ser publicado. Um artefato já existente para o mesmo SHA só é reutilizado se os bytes forem idênticos; conteúdo divergente nunca é sobrescrito. O manifesto registra Linux x86_64; o deploy/smoke na VM E2 Micro x86_64 continua bloqueado por PEND-003.

Qualquer árvore gerada antiga de release (`release` ou diretório de verificação `.incoming`) só entra em remoção recursiva, no Linux canônico, depois de comprovar ancestrais físicos, tipo de cada nó por `lstat` sem atravessar links, dispositivo compatível e ausência de mount na raiz ou em descendentes segundo o mesmo `mountinfo`. A árvore é retirada por `rename` atômico para um irmão exclusivo, e identidade, forma e mounts são revalidados no novo caminho antes de `rm`. Um arquivo gerado exato é removido apenas como arquivo físico; link ou nó especial é recusado. O gerador não é executado em Windows ou em plataforma sem essa prova Linux. Esse contrato impede que o cleanup atravesse volumes ou bind mounts esquecidos, inclusive no mesmo dispositivo, mas continua pressupondo ausência de um principal privilegiado que altere mounts ou a árvore concorrentemente.

Os launchers diretos `scripts/dev-all.mjs`/`scripts/release-manifest.mjs` e os workers em `tests/fixtures/` são entradas explícitas do Knip porque não dependem de import estático.

O comando npm do Knip é deliberadamente apenas `knip`. Valores E2E e URLs DAL/admin não podem ser materializados em `scripts`: o config já os lê do `.env.e2e.local` físico pelo helper do harness. ## 4. TypeScript

- `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `useUnknownInCatchVariables` e `verbatimModuleSyntax`;
- cada app executa `next typegen` antes de `tsc --noEmit`;
- packages possuem tsconfig próprio;
- `tsconfig.tests.json` cobre Playwright, Vitest, configs e helpers e resolve `@/` para o mesmo `src/` do app; o Vitest declara a mesma resolução para testar módulos reais sem substituir a fronteira de imports;
- o Vitest usa no máximo quatro workers, limitado pela paralelização realmente disponível no host, para não saturar criação de processos, PowerShell e Git no Windows. Testes que sobem um Vite SSR real ou constroem vários históricos Git declaram prazo próprio compatível com a operação comprovada; o restante conserva o timeout estrito padrão, sem retry ou tolerância global;
- `server-only` e `pg` já protegem o contrato de readiness; comandos de negócio continuarão restritos a módulos DAL server-only.

## 5. ESLint

- ESLint 9 e configs Next/TypeScript alinhados à versão do framework;
- regras React, hooks, Core Web Vitals, imports, ciclos, promises, `any` e `console`;
- imports de DAL/provider são proibidos em qualquer módulo com diretiva `"use client"` e nos diretórios visuais `components`/`packages/ui`, independentemente do caminho da feature;
- Server Components, route handlers e DAL fora das bordas visuais não recebem essa restrição por nome de pasta genérico;
- arquivos gerados e artefatos locais são ignorados explicitamente, nunca por exceção ampla.

## 6. Formatting

O Blueprint tem checksum canônico e não é reformatado. `scripts/format-scope.mjs` verifica todo código/config mantido e o Markdown alterado, inclusive depois do commit da branch. Entre `origin/main` e `main` local, a base Git escolhida é a candidata válida cujo `merge-base` está a menos commits de `HEAD`; assim uma ref remota atrasada não amplia o diff com trabalho já incorporado à `main` local. Em uma feature recém-criada no mesmo commit da candidata, o próprio `HEAD` é a base e somente mudanças working/staged/untracked podem exigir o novo registro; no checkout da própria `main`, a candidata idêntica continua cedendo ao histórico alcançável para preservar a verificação de seus commits. Empates preservam a precedência remota e, sem candidata útil, o gate usa o commit raiz alcançável; em um repositório ainda no commit inicial, todos os arquivos rastreados entram no conjunto. Os filtros incluem mudança de tipo Git `T`, portanto trocas entre arquivo regular e symlink permanecem no escopo documental e de formatação; antes de ler ou escrever qualquer candidato, o formatador rejeita symlinks e nós especiais com erro controlado, sem seguir um alvo externo. A ausência ou defasagem da ref remota nunca elimina Markdown commitado nem permite reutilizar um change record anterior. Prettier não substitui lint ou validação documental.

## 7. Playwright e axe

Pré-requisito de máquina:

```bash
npm run test:e2e:install
```

O config parseia `.env.e2e.local` sem contaminar `process.env`, rejeita origem/host/protocolo/porta remotos, exige `E2E_ALLOW_LOCAL=1` e comprova por conexão um marcador efêmero da instância. Depois que o runner Playwright é iniciado por uma toolchain confiável, um overlay neutraliza todos os nomes herdados antes do merge interno de cada webServer e restaura somente a allowlist operacional. No Windows, nomes são agrupados sem diferenciar caixa, variantes conflitantes falham e todo `ComSpec` herdado é substituído pelo arquivo físico `SystemRoot\System32\cmd.exe`, após prova de diretórios e leaf sem symlink/reparse. O comando usa o executável Node absoluto e um wrapper single-app versionado; esse wrapper reutiliza o mesmo guard dos comandos dev, relê o `.env.local` físico, valida a CLI Next fixada, preserva os valores runtime/anon locais, substitui somente `APP_ENV=test` e inicia Next diretamente, sem npm filho ou shell. Como Next é persistente, uma saída natural com código `0` é reclassificada como falha `1`; códigos não zero e sinais naturais preservam seu valor real. No POSIX, o prefixo `exec` mantém wrapper e Next no PGID que o Playwright controla; `SIGHUP`/`SIGINT`/`SIGTERM` são reconhecidos e encaminhados, e o fechamento solicitado conclui com limpeza `SIGKILL` do grupo. No Windows, o runner usa o guardian compilado e versionado do ADR-023; Next nasce suspenso, entra no Job Object e só então executa. Shutdown, saída natural ou perda do supervisor fecham o Job e eliminam descendentes sem utilitário auxiliar, PID reutilizável ou exposição do ambiente. Credencial administrativa, npmrc remoto, secrets e valores PG/SSH herdados não alcançam os apps após essa fronteira; cada app recebe somente sua DAL restrita e o runtime local validado. A matriz cobre 1440×900, 390×844, 320×720, altura compacta, backoffice isolado, axe claro/escuro/mobile e os fluxos críticos nos três engines, com retries zero e artefatos somente em falha.

O processo de cada browser recebe uma allowlist operacional independente do ambiente dos apps: paths/home/temporários, locale/fuso/terminal, variáveis gráficas locais não ligadas a Snap e os equivalentes mínimos do Windows. Segredos, URLs de banco, SSH, npm, opções Node, variáveis `SNAP*`, `LD_*`/`DYLD_*` e qualquer nome não enumerado nunca são herdados. Segmentos Snap e entradas vazias também são removidos do `PATH`/`Path`, evitando tanto bibliotecas do host incompatíveis quanto resolução pelo diretório atual.

`npm run test:e2e:install` usa a CLI Playwright fixada no workspace. Em Windows instala apenas os browsers; em Linux acrescenta `--with-deps` para as dependências do sistema. O opt-in `E2E_ALLOW_LOCAL=1` pertence ao `.env.e2e.local` protegido e não é mais injetado por uma atribuição POSIX no script npm.

## 8. Supabase local

Toda operação destrutiva ou administrativa do Supabase local adquire exclusão mútua antes da primeira inspeção do Docker e a mantém até o encerramento integral do wrapper. O lock é deliberadamente host-global e independente do checkout: Windows usa o mutex de kernel nomeado `SetLivre.SupabaseLocal.v1`, mantido por um subprocesso do Windows PowerShell 5.1 físico `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` enquanto o pipe do processo Node permanecer aberto; Linux usa `/usr/bin/flock` em modo exclusivo e não bloqueante sobre o descritor do inode estável `/tmp/set-livre-supabase-local-v1.lock`, que nunca é removido. Os dois mecanismos são fail-fast, liberados pelo kernel após saída ou crash e não usam PID, timestamp ou remoção de lockfile para inferir abandono. O helper Windows recebe somente `SystemRoot` e `WINDIR`, não usa shell nem override de execution policy, recupera `AbandonedMutexException` como posse válida e faz o processo dono encerrar fail-closed se o guardião desaparecer durante uma operação. `local:setup`, `supabase:start`, `supabase:stop`, `supabase:status`, `supabase:reset`, `supabase:schema`, `supabase:types` e `test:db` atravessam essa fronteira; uma segunda invocação termina com diagnóstico fixo antes de Docker, Supabase, PostgreSQL ou qualquer secret herdado serem inspecionados.

`npm run supabase:reset` executa:

1. comprovação do daemon Docker;
2. no Windows, abertura física e estável do `settings-store.json` do perfil e exigência do setting oficial `PortBindingBehavior=local-only-port-binding`; criação idempotente da bridge `set-livre-loopback`, cujo default de publicação também é `127.0.0.1`;
3. validação específica da publicação: Linux exige `HostIp=127.0.0.1` literal em cada porta; no Docker Desktop Windows, aceita-se somente o bind literal ou o par local-only `127.0.0.1` + `::` com `HostConfig.HostIp=""`; `0.0.0.0` nunca é tolerado;
4. parada restrita à stack `set-livre` se containers preexistentes estiverem em outra rede ou binding;
5. `supabase start --network-id set-livre-loopback`, validação dos bindings efetivos e `supabase db reset --local`;
6. migrations e seed;
7. autenticação local explícita como `supabase_admin` superuser, usando a mesma credencial efêmera da stack e sem expô-la, para fechar `public`/`net`, defaults gerenciados, catálogos sensíveis e membros residuais de `app_dal`/login;
8. criação/rotação local de `app_runtime_local` com estado exato e somente `CONNECT` direto;
9. reconciliação exata das duas referências a `app_dal`: `postgres` administrativa sem `SET/INHERIT` e runtime sem `ADMIN/INHERIT` com `SET` explícito;
10. smoke da identidade efetiva e das duas probes privadas de readiness antes de publicar qualquer ambiente;
11. gravação separada dos dois `.env.local` de runtime e de `.env.e2e.local`, sem imprimir secrets; POSIX exige modo `0600`, e Windows exige arquivo físico sem reparse point, owner esperado e DACL protegida limitada ao usuário atual, `SYSTEM` e administradores.

No Windows, o operador seleciona **Settings → Resources → Network → Port binding behavior → Localhost only** no Docker Desktop. O wrapper não confia apenas na UI: valida caminho canônico do perfil, ausência de reparse point, arquivo físico regular, tamanho máximo, chave única e identidade estável por descritor antes e depois da leitura. A inspeção Docker exige exatamente Kong `8000/tcp→54321`, Postgres `5432/tcp→54322`, Studio `3000/tcp→54323` e Inbucket `8025/tcp→54324`; UDP, wildcard IPv4, porta trocada/extra/duplicada, bind divergente, mistura de modos, `HostConfig.HostIp` não vazio ou contexto Docker não canônico são recusados. Uma prova funcional adicional confirmou listeners somente em `127.0.0.1` e falha de conexão pelas interfaces não-loopback. A antiga regra customizada do Windows Firewall e seus comandos npm foram removidos: a fronteira agora possui uma única autoridade suportada pelo produto. A stack continua temporária e deve terminar em `npm run supabase:stop`. Linux e CI permanecem no bind literal `127.0.0.1`.

O setting `Localhost only` está ativo e foi comprovado pelo wrapper e pelos listeners efetivos. A cadeia Supabase local limpa contém 16 migrations, predecessor `20260815000100` e head `20260819000100`; `supabase:reset`, geração canônica e `test:db` comprovaram o estado local. O pgTAP passou em 4 arquivos e 361/361 testes, com readiness de 17 dependências ACL e 16 rotinas DAL. Essa prova é local e não implica schema/migrations no projeto Cloud de São Paulo, VM, PR ou deploy; os demais gates do SHA final permanecem pendentes.

A normalização e a probe usam o driver `pg@8.23.0` fixado no workspace, não um executável `psql` descoberto no host. A conexão aceita somente o PostgreSQL local em `127.0.0.1:54322`, força `ssl: false`, aplica timeouts explícitos e remove variáveis `PG*`/`PSQL*` herdadas. Antes de continuar, a sessão comprova `current_user`, `session_user`, banco e timeouts esperados; a probe DAL assume somente a role local restrita. O mesmo bootstrap funciona em Windows 11 nativo e Linux. O `psql 18.6` instalado no Windows fica disponível apenas para diagnóstico manual do operador e não participa da autoridade do setup. A CLI Supabase também não é global nem passa pelo launcher JavaScript do pacote: o executor valida os manifests raiz, `supabase@2.115.0` e o pacote nativo opcional da mesma versão, então executa diretamente o arquivo físico absoluto `node_modules/@supabase/cli-windows-x64/bin/supabase.exe` no Windows x64 ou `node_modules/@supabase/cli-linux-x64/bin/supabase` no Linux x64. Plataforma, arquitetura, versão e integridade do caminho precisam corresponder ao contrato; não há `npx`, lookup em `PATH`, `node_modules/supabase/dist/supabase.js` ou CLI global. No Windows, o ambiente filho é reconstruído por allowlist case-insensitive, preserva somente dados operacionais explícitos como `DOCKER_HOST` e elimina qualquer caixa de `NODE_OPTIONS`, `NODE_PATH`, `SUPABASE_CLI_BINARY_OVERRIDE`, secrets e nomes desconhecidos. O instalador de browsers aplica o mesmo contrato ao `@playwright/test@1.62.1`.

A URL administrativa fica em `E2E_DATABASE_URL` somente no arquivo do harness. Runtime usa `DATABASE_URL_APP_DAL` com `SET ROLE app_dal`. Antes de qualquer branch, inclusive `stop`, bootstrap e wrappers recusam overrides Docker remotos. Em Windows, aceitam somente `default` no named pipe local `npipe:////./pipe/docker_engine` ou `desktop-linux` em `npipe:////./pipe/dockerDesktopLinuxEngine`; em Linux, preservam o socket local autorizado. Em todos os casos exigem `OSType=linux`, pinam o endpoint no ambiente de cada comando Docker/Supabase e recusam TCP, SSH ou contexto remoto. Os wrappers de start/status/test/dump/types recusam stack fora da bridge; todo `stderr` fica em pipe privado e é descartado, falhas substituem integralmente buffers e erro original, e o status completo com chaves nunca é impresso. Somente o `stdout` necessário a pgTAP e geração de tipos pode ser herdado. Nenhuma migration contém senha e nenhum comando usa `supabase link` ou cloud.

## 9. Knip e supply chain

Knip descobre os quatro workspaces pelos manifests/configs. No workspace raiz, `supabase` é a única entrada de `ignoreDependencies`: o executor lê o manifesto e resolve dinamicamente o pacote nativo opcional da plataforma, sem import estático do pacote agregador, mas a dependência continua fixada e efetivamente usada. No pacote UI, `@types/react-dom` permanece ignorado por ser necessário ao contrato JSX sem import runtime. As exceções de `ignoreBinaries` também são fechadas: `flock` atende a release/deployer Linux, `mkfifo` atende ao deployer e aos testes POSIX, e `reg.exe`/`where.exe` são usados somente pelo teste de contrato Windows que localiza a instalação física do PowerShell 7. Essas exceções não ocultam outro package npm, import ou código morto. `npm audit --audit-level=high`, `ignore-scripts=true`, `strict-allow-scripts=true` e `dangerously-allow-all-scripts=false` completam o gate: `npm ci` não executa lifecycle de dependência, root ou workspace, nenhuma entrada `allowScripts` é aceita e um override isolado de `ignore-scripts` ainda falha no preflight estrito. Esse contrato pressupõe a invocação canônica sem override `NPM_CONFIG_*` hostil; um chamador já comprometido está fora da fronteira.

`docs:check` também calcula o conjunto externo direto dos quatro manifests canônicos, incluindo dependências de runtime, desenvolvimento, opcionais e peers. Cada pacote precisa aparecer uma única vez em `docs/dependencias-utilizadas.md`, com nome e versão semver exatos, superfície, licença, justificativa e avaliação de supply chain; registros ausentes, extras, agrupados, duplicados ou incompletos falham. Specs com alias npm, faixa ou formato ambíguo também falham. Enquanto o registro não representar replacements sem ambiguidade, qualquer `overrides` não vazio é recusado, inclusive troca de versão ou alias para outro pacote. Dependências `@set-livre/*` não entram como terceiros: o gate exige que apontem exatamente para nome e versão de um dos workspaces físicos canônicos.

## 10. Docs check

O gate falha, entre outros casos, quando:

- o Blueprint muda sem novo contrato;
- feature, cenário ou ADR duplica ID;
- a sequência não contém exatamente as 34 features;
- `dependency-to-start` cria ciclo ou aponta para frente;
- integração posterior não possui proprietário;
- dependência de release não referencia `pendencias.md`;
- link local está quebrado;
- dependência proibida entra em qualquer seção instalável, substituível ou empacotável de qualquer workspace; a política canônica e fechada cobre nomes, scopes e prefixos delimitados mantidos de ORM/query builder, Tailwind/shadcn, CSS-in-JS — inclusive Griffel pelo scope `@griffel/` —, primitives MUI pelo scope `@mui/`, Redux/Zustand e clientes remotos alternativos, Redis/Kafka/filas, Docker/Kubernetes, Caddy e CMS; o manifesto raiz precisa preservar exatamente `apps/*` e `packages/*`, os três manifests de workspace precisam ser arquivos físicos no conjunto canônico e nenhum outro diretório imediato pode casar os globs; o denylist cobre dependências runtime, desenvolvimento, opcionais, peers, bundles, aliases `npm:` e overrides aninhados, além de recusar hooks de instalação, `binding.gyp` implícito, shrinkwrap ou lock paralelo no root/workspaces; specs diretas ou replacements por URL, Git, tarball ou arquivo local também são recusadas;
- qualquer dependência direta externa dos quatro manifests diverge do registro exato de versão, superfície, licença, justificativa e supply chain em `docs/dependencias-utilizadas.md`, ou o registro possui pacote stale/ambíguo; aliases npm, ranges e `overrides` não vazio são recusados pelo contrato canônico;
- uma migration muda caminho, blob, tipo ou modo depois do commit que a introduziu em qualquer snapshot `first-parent` desde a base segura; antes de qualquer leitura Git, `--show-toplevel` precisa coincidir por caminho canônico, dispositivo e inode com a raiz física auditada e ambos os lados são revalidados. Assim `core.worktree` não pode substituir silenciosamente a árvore, mas um linked worktree real continua aceito pela sua própria raiz. Checkout com `HEAD` em clone shallow, com `refs/replace` ou `info/grafts` legado não vazio falha antes de confiar no grafo. Base ancestral apenas por outro parent, flag não canônica no índice, divergência no índice/worktree, nó não físico, nome inválido, versão repetida ou versão que não avança o head anterior também falham. O gate lê cada migration indexada pela fronteira física estável, calcula diretamente seu blob com `git hash-object --no-filters --stdin` em ambiente fechado e compara também o modo executável, sem confiar no stat cache ou em configurações locais que ocultem conteúdo ou `chmod`. A varredura inversa exige ainda que cada entrada física esteja indexada ou seja listada canonicamente como untracked por `git ls-files --others --exclude-standard`; migrations ocultas por qualquer regra de ignore falham, mas uma adição visível continua válida antes do stage. Várias adições no mesmo commit são permitidas quando todas avançam o head anterior; bootstrap sem `HEAD` e commit raiz preservam a cadeia inicial sob os demais contratos físicos e de nome;
- código contém marcador de dívida informal;
- Playwright contém `.only`, `.skip` ou `waitForTimeout`;
- um intervalo de features na tabela normativa ou em `pendencias.md` é descendente;
- uma mudança em código, testes, banco ou qualquer configuração mantida, na raiz ou aninhada — inclusive dotfiles, exemplos de ambiente, versões de runtime, configs JSON/TypeScript, contratos legíveis por máquina como `docs/feature-sequence.json` e a lista fechada de entrypoints raiz `proxy`, `middleware`, `instrumentation`, `instrumentation-client` e `mdx-components` — não possui registro em `docs/changes/`;
- o registro correspondente em `docs/changes/` foi apenas modificado, renomeado ou excluído: o gate exige ao menos um Markdown com status Git `A`, não vazio, ainda presente como arquivo físico regular exclusivo sob raiz e ancestrais físicos; a abertura usa `O_NOFOLLOW` e a leitura revalida descritor, caminho e ancestrais contra trocas concorrentes;
- uma mudança técnica não atualiza `contexto-projeto-set-livre.html`, ou o resumo executivo deixa de ser HTML5 autônomo, em português, com estrutura mínima de produto, aplicações, arquitetura, scripts, testes, segurança, release, features e próximos passos;
- nenhuma base Git segura pode ser lida; a mesma seleção pelo `merge-base` mais próximo, com fallback no commit raiz, usada pelo formatador preserva mudanças já commitadas sem aceitar registros herdados de uma `main` local mais nova que `origin/main`.
