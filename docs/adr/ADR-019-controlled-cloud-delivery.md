# ADR-019 — Entrega cloud controlada para Set Livre

## Status

Aceito em 2026-08-16 por instrução humana explícita.

## Contexto

O Blueprint, seções 6, 19, 23, 24 e 26, e o ADR-014 exigem CI, Supabase Cloud e uma VM Oracle Linux com release imutável. O ADR-018 suspendeu temporariamente essas ações durante a fundação local-first. O responsável do produto criou o projeto Supabase `set-livre`, adquiriu `setlivre.com` e autorizou a implantação da fronteira de entrega cloud. O projeto criado está em `ca-central-1` e não é o alvo de produção; o projeto produtivo em `sa-east-1` (São Paulo) ainda precisa ser criado e comprovado. O ADR-021 substitui o alvo A1/ARM64 originalmente adotado por `VM.Standard.E2.1.Micro` x86_64.

A autorização não elimina os contratos locais: banco, Auth e testes destrutivos continuam no Supabase local; credenciais cloud não entram em PRs; produção não usa Docker; migrations aplicadas continuam append-only. Também não autoriza provider de pagamento, SMTP, observabilidade externa ou qualquer integração ainda suspensa pelo ADR-018.

## Decisão

- este ADR substitui somente a proibição temporária do ADR-018 sobre `.github/workflows`, Supabase Cloud, Oracle Cloud, DNS, TLS e secrets de deploy;
- a suspensão de APIs/providers externos do ADR-018 permanece vigente até decisão própria;
- todo merge destinado a release segue o contrato fail-closed de
  [`docs/review-deploy-cycle.md`](../review-deploy-cycle.md): PR não draft, ciclos de `@codex review`
  separados por pelo menos 60 minutos, inspeção de todas as superfícies, correção/teste dos findings e
  declaração explícita de review limpo para o SHA final. Novo push reinicia a espera; timeout ou
  ausência de resposta são inconclusivos. Falha pós-merge volta por nova branch/PR, nunca por edição
  manual de produção;
- `.github/workflows/ci.yaml` executa os gates normativos em runner efêmero Ubuntu, Node `24.18.0`, npm `11.19.0`, driver `pg` do lockfile, Docker e Supabase local isolado; PR não recebe secret de produção, e cada `push` de `main` usa grupo por SHA sem cancelamento;
- o workflow de produção só é elegível após CI verde no `push` de `main`, SHA completo, `workflow_run.path=.github/workflows/ci.yaml`, repositório do run e repositório de origem iguais ao repositório atual e variável **de repositório** explícita `PRD_DEPLOY_ENABLED=true`; a mesma variável é copiada para o host e ambas permanecem `false` até a prova operacional completa;
- como o repositório é público, build/package de produção roda exclusivamente em GitHub-hosted Linux x86_64, sem secrets server-side nem mutação, e publica o artifact por action fixada por SHA. Nenhum runner self-hosted executa código do GitHub dentro da VM;
- os workflows validam a cadeia de runs pela API com `actions/github-script` oficial `v9.0.0`, fixada por SHA completo e permissões `actions: read`/`contents: read`; isso elimina token em configuração curl, arquivos JSON temporários e validadores Python inline. Um agente pull outbound-only sob principal sem login consulta os artifacts aprovados. Antes de qualquer mutação, valida identidade de repositório/workflow/run, branch `main`, SHA, digest fornecido pela API, tamanho, nome, manifesto schema 4, hash canônico da configuração pública, runtime Linux x86_64 e ancestralidade monotônica; origem da release e run provedor do artifact são identidades distintas, e somente a origem ordena/checkpointa a fila. A CLI Supabase não pertence ao artifact: o bootstrap instala a release oficial fixada como ferramenta root-owned do host, e o agente valida caminho, owner/modo, versão, ELF x86_64 e hashes antes de capturar secrets ou iniciar migration. Identidade/SHA divergente, ferramenta host divergente, ordem inesperada, replay divergente ou downgrade falham fechados. Toda chamada `curl` remanescente no agente da VM ignora configuração ambiente antes de receber headers de autenticação;
- o repositório fixa `SET_LIVRE_REPOSITORY_ID=1328339374` e, depois que a `main` materializar os paths, exige `CI_GITHUB_WORKFLOW_ID`/`PRD_GITHUB_WORKFLOW_ID` como repository variables. O host conserva os mesmos fatos como `GITHUB_REPOSITORY_ID` e os dois workflow IDs. Eles são obtidos somente dos endpoints dos paths registrados `.github/workflows/ci.yaml` e `.github/workflows/prd-deploy.yaml`; ausência, `404`, estado não ativo, path divergente, desigualdade entre GitHub/host ou IDs iguais mantém as duas travas `PRD_DEPLOY_ENABLED=false`;
- o agente não recebe conexão inbound do GitHub, chave de deploy ou credencial SSH. A porta 22 permanece exclusiva do CIDR administrativo humano `/32`;
- produção usa exclusivamente um projeto Supabase Set Livre comprovado em `sa-east-1` (São Paulo), selecionado pelo contrato canônico do workflow e do Environment; o projeto existente em `ca-central-1` não recebe migrations nem tráfego de produção. O pipeline aceita somente migrations versionadas com `supabase db push`, primeiro em `--dry-run`, e nunca executa `db reset`, seed ou `config push` remoto. O primeiro deploy estabelece a baseline versionada; todo delta posterior exige marcador `-- set-livre:migration-mode=expand-only`, passa por recusa fail-closed de contrações conhecidas e preserva a release N-1;
- o artifact assina também um catálogo SQL somente leitura e um contrato semântico exato da transição N−1/N. O gerador aplica cada head no Supabase local, captura relações, RLS, policies e ACLs efetivas por objeto, registra adições e remoções canônicas e exige aprovação explícita para toda ampliação. O agente persiste o snapshot Cloud anterior antes do push e recusa o deploy se o delta ou o estado posterior divergirem; policy pública de escrita, grant perigoso, grant option, `CREATE` de schema/database/tablespace e autoridade equivalente permanecem proibidos mesmo que alguém tente incluí-los na allowlist;
- configurações Auth, redirects, SMTP, captcha, Storage e secrets do projeto são ações humanas auditáveis; `supabase/config.toml` permanece local e não é enviado ao Cloud;
- a cadeia local atual contém 16 migrations. O runtime conecta ao banco somente por login restrito capaz de assumir `app_dal`; o deploy prova `private.check_runtime_readiness(session_user)`, cujo manifesto confere 17 dependências ACL e 16 rotinas DAL, valida separadamente o head remoto exato e usa uma janela de compatibilidade explícita que aceita `20260819000100` e o predecessor `20260815000100` enquanto o head permanece exatamente `20260819000100`;
- a release é construída nativamente em Linux x86_64 no runner GitHub-hosted, contém os standalones web/backoffice, migrations, lockfile e manifesto schema 4, sem CLI ou ferramenta administrativa, e é identificada pelo SHA completo. O manifesto contém somente o SHA-256 do JSON público canônico, nunca as URLs/chave em claro; a passagem para a VM ocorre somente por download outbound do artifact aprovado, nunca por SSH;
- o agente roda sob usuário/grupo dedicados, mantém staging privado e só pode chamar sem senha um dispatcher root-owned com argumentos allowlisted; o grupo efetivo contém exatamente esse principal e a inspeção estruturada de `sudo -ll` admite exatamente uma entrada root para `/usr/local/sbin/setlivre-deploy-dispatch`, sem `setenv`, sudo genérico ou execução direta do release manager;
- bootstrap e instalação do agente são operações separadas: `bootstrap-oracle-host.sh` aceita somente `<admin-cidr-/32> <release-manager-source> <release-manager-sha256>`, congela e valida a fonte antes de qualquer pacote e não recebe deploy public key/user/SSH; depois `configure-production-deployer.sh` instala e verifica agente, smoke, dispatcher, sudoers e timer systemd por hashes fixados. Atualizações futuras do manager passam exclusivamente por uma transação administrativa root-owned, com preparação, troca atômica, verificação e restauração do binário anterior; agente e artifact nunca recebem essa autoridade;
- a sandbox systemd do agente libera escrita somente em `/var/lib/setlivre-deployer/.setlivre`, `/opt/setlivre` e `/run/lock`; `/run` inteiro, path adicional ou relaxamento equivalente é rejeitado;
- a VM segue os ADRs 014 e 021: `VM.Standard.E2.1.Micro` x86_64, Ubuntu 24.04, Nginx, systemd, processos sem root e release manager root-owned protocolo v3. O manager copia o staging para área root-owned, valida checksum, manifesto schema 4, árvore, runtime, head e hash da configuração pública antes de qualquer migration, e a ativação revalida exatamente os mesmos bytes. Release, runtime, proveniência, estados e diretórios de symlink são sincronizados depois de cada publicação atômica. Uma unit root-owned recupera e prova um único estado `pending` antes de web, backoffice e Nginx iniciarem, inclusive com links `current` divididos, e só então libera tráfego;
- depois do push/readiness do banco e antes da ativação, o agente executa smoke público curto da release N-1 contra o schema migrado. Só então troca `current`, arma o lease/watchdog de 20 minutos e monitora o novo SHA por 15 minutos; live/ready precisam declarar `application` e `release` exatos, e os smokes cobrem home, login, backoffice, negação Auth e redirects HTTP canônicos. `confirm` persiste e sincroniza o estado confirmado antes de desarmar o watchdog. Falha interna, HTTPS, redirect, interrupção ou ausência de confirmação restaura e volta a testar a release anterior; no primeiro deploy falho, remove a ativação e comprova os serviços inativos;
- nenhuma VM ou rede é criada sem prova read-only de home region, compartment, AD, quota, shape, imagem, VCN/subnet, chave SSH e elegibilidade Always Free; nomes ou redes de outros projetos nunca são reutilizados por conveniência. Em 2026-08-18, uma instância diagnóstica `set-livre-production` foi comprovada `RUNNING` em `sa-saopaulo-1`, na rede isolada `10.20.0.0/16` e subnet `10.20.1.0/24`, com `VM.Standard.E2.1.Micro`, boot 50 GB, IMDSv2-only e SSH administrativo confirmado. Ela e o boot volume foram depois terminados para eliminar o host parcial; novos Plans precisam voltar a provar capacidade antes do reprovisionamento. A evidência histórica não comprova VM ativa, hardening ou deploy;
- DNS e TLS só avançam depois de comprovar tipo e permanência do IPv4 público da VM ativa, firewall/NSG mínimo e origem inequívoca; uma substituição de VM/VNIC/endereço exige atualização de DNS. IP `RESERVED`, estabilidade permanente ou gratuidade não são presumidos e dependem de nova decisão/evidência. Renovação TLS é responsabilidade operacional do host, não uma reparação destrutiva em cada deploy;
- o GitHub Actions recebe somente variáveis públicas necessárias ao bundle, além da variável de repositório `PRD_DEPLOY_ENABLED`; nenhum secret Supabase/DAL fica no repositório ou Environment. A chave pública `PRD_SUPABASE_ANON_KEY` existe como repository variable e também no runtime do host. `GITHUB_DEPLOY_TOKEN`, os três IDs operacionais, `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD` e `PRD_DATABASE_URL_APP_DAL` ficam exclusivamente em `/etc/setlivre-deployer/production.env`, root-owned e `0640`; os IDs não são secretos, mas pertencem ao contrato exato do host. Nenhum segredo entra em argumento público, bundle, artifact, log, screenshot ou documento;
- o agente acompanha os jobs de cada merge até estado terminal e corrige falhas por novo patch/PR; workflow não recebe permissão para alterar código ou contornar review automaticamente.

## Alternativas

- continuar somente local: rejeitado para a fronteira de infraestrutura porque o responsável liberou os recursos e pediu deploy pós-merge;
- reutilizar VCN/compartment de Spenses ou de outro projeto: rejeitado por isolamento, blast radius e auditoria;
- executar Docker Compose em produção: rejeitado pelo Blueprint e ADR-014;
- aplicar `schema.generated.sql` ou reset remoto: rejeitado porque migrations são a história canônica e produção é forward-only;
- fazer deploy direto no fechamento de qualquer PR: rejeitado porque não prova CI do SHA já incorporado a `main`;
- usar runner hospedado pelo GitHub com SSH para a VM: rejeitado porque exigiria ingress operacional variável na porta 22 e credenciais SSH no workflow;
- usar runner self-hosted na VM de repositório público: rejeitado porque código de workflow/PR não confiável poderia persistir no host de produção;
- dar sudo amplo ao agente: rejeitado; apenas o dispatcher root-owned com comandos/argumentos fechados pode cruzar a fronteira privilegiada;
- armazenar service role ou credencial administrativa no runtime: rejeitado pelos ADRs 005 e 014.

## Consequências

- CI e deploy passam a existir como código, mas ficam fail-closed até os itens humanos de `configuration-seteps.md` e o primeiro run real serem comprovados. `PRD_DEPLOY_ENABLED=false`; o projeto Supabase de São Paulo ainda não foi criado, o projeto canadense não é produção e nenhuma migration Cloud foi aplicada. A VM E2 diagnóstica aceitou SSH em 2026-08-18, mas foi terminada com o boot volume. Na última evidência OCI preservada (`2026-08-19T09:45:42Z`), não havia VM Set Livre ativa e o Plan E2 reportava `OUT_OF_HOST_CAPACITY`; hardening, agente/secrets do host e DNS/TLS continuam pendentes. O PR, os ciclos de review, o merge e o deploy desta fundação ainda não foram executados. O Environment build-only não recebe secrets nem muta produção; enquanto houver um único colaborador, autoaprovação não é aceita como controle. A autorização usa ciclos limpos de `@codex review`, merge protegido e travas independentes no repositório e no host;
- o build/package Linux x86_64 depende do runner GitHub-hosted adotado; mutação/ativação dependem do hardening da VM e da instalação do agente pull. A fonte atual ainda não foi executada em produção;
- migrations podem permanecer após rollback do app; por isso toda mudança de schema de release precisa ser expand/migrate/contract, trazer o marcador obrigatório nos deltas posteriores à baseline, declarar a janela compatível, passar no smoke N-1 pós-migration e provar o head remoto exato separadamente;
- uma VM continua sendo ponto único de falha; backup, restore drill, monitoramento e patching são obrigatórios antes do go-live;
- quando ativa, a instância Set Livre ocupa a segunda e última posição E2 Micro Always Free da tenancy; na evidência de `2026-08-19T09:45:42Z`, a posição lógica estava liberada e faltava capacidade física. Substituição paralela, escala horizontal ou shape pago exigem nova decisão e evidência de custo;
- ADR-018 continua normativo para pagamentos e demais APIs externas não liberadas.
